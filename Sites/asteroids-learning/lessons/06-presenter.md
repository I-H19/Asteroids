# 6. Presenter: связать экран с игрой и не знать устройство всего проекта

Разбор от 9 октября 2026 года по текущим исходникам и двум новым замечаниям ментора. Скриншоты использованы как учебный материал; игровой код не изменён, сцена не запускалась.

Это три последовательные практики: **граница View → источник данных → жизненный цикл**. Можно пройти их отдельно от остальных занятий. Цель — самостоятельно исправить оба замечания и объяснить, почему выбранные границы работают.

## Теория, которая нужна именно здесь

В примере MVP на твоих скриншотах выбран вариант Passive View: View сообщает о действиях пользователя, Presenter обращается к модели и передаёт View подготовленные данные. View не извлекает сведения из игровых объектов. Это полезная учебная цель; варианты MVP могут отличаться распределением простого форматирования и синхронизации. Основной смысл Passive View — отделить отображение от модели и сделать поведение представления проверяемым без настоящих UI-компонентов. [Описание Мартина Фаулера](https://martinfowler.com/eaaDev/PassiveScreen.html).

Фразу «Presenter тупо передаёт события и данные» понимай как ограничение ответственности. Presenter может выбирать, что показать, форматировать число и передавать пользовательскую команду. Правила начисления очков, расчёт перезарядки и обход компонентов корабля — отдельные обязанности.

Model в диаграмме — роль, а не требование упаковать всю игру в один `GameModel`. В твоей игре уже есть источники состояния и команды: оружие, движение, реестр, завершение и рестарт. Для экрана можно предоставить небольшой согласованный набор данных и операций поверх них. Уменьшить число полей, спрятав всё в один объект с десятками методов, недостаточно.

Не нужно переписывать проект на MVC или MVVM. Эти замечания можно разобрать внутри MVP из скриншотов.

Часть работы уже на месте: Presenter не уничтожает врагов при рестарте, а вызывает `GameRestarter`. View управляет текстами и видимостью панели. Задача — уточнить границы, сохранив эти полезные разделения.

Нарисуй две текущие цепочки:

`Button → Presenter → GameRestarter`

`Laser / mover / rotator / Rigidbody2D → Presenter → PlayerStats → GameView`

Вопрос перед работой: при замене кнопки на другое средство ввода и при замене устройства движения какие части Presenter придётся менять? Ответы станут проверками после рефакторинга.

## Практика A. View сообщает намерение пользователя

### Шаг 1. Отделить клик от команды

В черновике напиши две фразы: «нажата Unity Button» и «пользователь запросил новую игру». Первая описывает технический способ ввода, вторая — смысл действия.

Придумай публичное событие View для второго случая. Какой минимальный набор аргументов ему нужен? Обязательно ли передавать саму кнопку?

Для разминки сделай обычный C#-класс с событием `Action` и методом, который его вызывает. Подпиши внешний обработчик. Проверь, что издатель не хранит ссылку на конкретный класс подписчика. Затем отпиши обработчик и повтори вызов.

Здесь три разных действия: `+=` подписывает; `Invoke` сообщает о событии; `-=` прекращает подписку. Если их смысл ещё путается, остановись на этом маленьком опыте.

### Шаг 2. Провести событие через настоящее View

1. Выбери владельца ссылки на кнопку: `GameView` либо отдельное View панели рестарта. Если выбран второй вариант, явно реши, кто передаёт его событие дальше.
2. Внутри View свяжи `onClick` со своим событием намерения.
3. Подпиши Presenter на событие View вместо `Button.onClick`.
4. Убери параметр `Button` из инициализации Presenter и проверь, осталась ли в нём необходимость в `UnityEngine.UI`.
5. Измени сборку в [SceneEntryPoint.InitializeUI](<C:/Program Files/UnityProjects/Asteroids/Assets/_Project/Sources/GameLoop/SceneEntryPoint.cs>): кнопка теперь нужна выбранному View.

Не заменяй поле кнопки на `_view.RestartButton.onClick`: Presenter по-прежнему будет работать с устройством UI. Его новый договор должен описывать запрос пользователя.

Необязательно сразу менять хранение всех ссылок в [RootUI](<C:/Program Files/UnityProjects/Asteroids/Assets/_Project/Sources/UI/RootUI.cs>). Передавать UI-компоненты во View из места сборки допустимо. Важен получатель: Presenter не должен их использовать.

### Шаг 3. Выбрать момент подписки

На скриншоте кнопка сериализована во View, поэтому пример подписывается в `Awake`. В твоём `GameView` зависимости сейчас приходят через `Init`. Нарисуй порядок «создание объекта → получение ссылки на кнопку → подписка». Будет ли ссылка уже доступна в `Awake`, если ты сохранишь передачу через `Init`?

Выбери один согласованный жизненный цикл: подписка после получения зависимостей и соответствующая отписка, либо цикл включения/выключения для уже настроенного View. Продумай повторное включение панели. `OnEnable` не должен использовать ещё не переданные ссылки, а каждый повторный `Init` — добавлять новый обработчик.

Существующий `RemoveAllListeners()` снимает все непостоянные обработчики UnityEvent, добавленные из кода, включая чужие; обработчики Inspector он не удаляет. Для своей подписки нужна адресная отписка. [Документация Unity](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Events.UnityEventBase.RemoveAllListeners.html).

Если используешь лямбду и хочешь снять её позже, сохрани тот же делегат; заново написанная похожая лямбда — не надёжный способ отписаться. Именованный метод упрощает этот учебный этап.

### Проверка A

- Один клик вызывает один запрос и один рестарт.
- Закрытие/открытие панели несколько раз не умножает запросы.
- Presenter не содержит `Button`, `onClick`, `AddListener`, `RemoveAllListeners` и не получает кнопку через свойства другого объекта.
- Временный второй способ ввода внутри View может поднять то же событие без изменения Presenter.
- После уничтожения View либо завершения жизни Presenter соответствующие подписки сняты.

Остановись здесь и проверь сцену перед следующей практикой.

## Практика B. Данные экрана не должны собираться в Presenter из устройства корабля

### Шаг 4. Найти источник истины

Заполни таблицу самостоятельно:

| Данные | Кто реально владеет ими сейчас? | Кто сейчас копирует их для UI? | Кто должен обновлять их без UI? |
|---|---|---|---|
| Скорость | ... | ... | ... |
| Позиция | ... | ... | ... |
| Боезапас и cooldown | ... | ... | ... |
| Счёт | ... | ... | ... |
| Состояние «игра завершена» | ... | ... | ... |

В `PlayerStats` уже есть набор значений, но этот класс не получает игровые события самостоятельно и не уведомляет об изменениях. Само наличие класса с данными пока не образует канал «модель изменилась → Presenter обновил экран».

Мысленный опыт: Presenter отсутствует, но игровая сцена продолжает работать. Будет ли обновляться счёт в `GameModel`? Будут ли актуальны значения `PlayerStats`? Найди конкретных вызывающих `ScoreIncrement` и `ChangeSpeed`.

Так проверяется зависимость игровых правил от экрана. Просто выключить Canvas для этого недостаточно: обычный C#-Presenter может продолжать работать и получать события.

### Шаг 5. Начать с одного значения

Выбери скорость. Опиши минимальный источник данных, который нужен Presenter: текущее значение и уведомление, когда оно изменилось. В этом договоре не должно требоваться получение `InertialMover` или `Player`.

Реши, кто вне Presenter связывает реальный источник скорости с этим договором. Возможны небольшой адаптер телеметрии или развитие текущей модели данных с отдельным связующим объектом. Сначала нарисуй обязанности и только потом давай классам имена.

Для первой попытки перенеси один маршрут скорости и проверь его. После этого аналогично разберись с остальными показателями. Не начинай с универсального сервиса событий для всей игры.

Проверка границы: если заменить `InertialMover`, должен измениться код получения скорости из игры, а Presenter должен продолжить работать с тем же понятным значением.

Копия данных для HUD допустима. Запиши, кто единственный её обновляет и когда она актуальна. Если и Presenter, и новый адаптер меняют один `PlayerStats`, ответственность ещё не определена.

### Шаг 6. Отделить счёт и команды от сбора телеметрии

У скорости есть существующий источник, а счёт сейчас увеличивается по инициативе Presenter. Разбери его отдельно: кто должен связывать `ScoredKilled` с правилом начисления и `Restarted` со сбросом? Результат должен сохраняться, даже если экран временно не подключён.

Для рестарта оставь команду игровому слою. Спрятать, как удаляются враги и сбрасывается игрок, уже помогает `GameRestarter`. Presenter может передать ему запрос напрямую через узкий договор или через согласованный API модели/сессии. Наличие такой зависимости само по себе не ошибка. Не нужно переносить очистку врагов в Presenter ради «единого управления».

Не превращай `GameModel` в новое место, которое знает Button, Rigidbody2D, все фабрики и каждый экран. Раздели как минимум смысл: данные для отображения, игровые правила, команда рестарта. Это может быть несколько небольших объектов; их количество не является оценкой качества.

### Шаг 7. Довести Passive View до выбранной границы

Сейчас `GameView.ChangeHUDStats(PlayerStats)` читает объект данных и собирает строки. В строгом варианте из твоих скриншотов подготовку текста выполняет Presenter, а View получает готовые значения для показа.

Выбери один показатель, например строку боезапаса. Определи отдельно:

- расчёт количества доступных зарядов — правило оружия;
- превращение двух чисел в текст вида «2 / 5» — подготовка представления;
- запись текста в TMP-компонент — работа View.

Сначала проведи этот маршрут целиком, затем остальные. Можно передавать отдельные строки либо небольшой набор подготовленных данных экрана. Передаваемый объект не должен открывать View доступ к живому `Player` или игровым командам.

Количество строк Presenter после переноса форматирования может даже вырасти. Оценивай причины изменения и зависимости, а не только длину класса.

### Проверка B

- Presenter больше не извлекает Rigidbody2D, mover, rotator и Laser из Player.
- Источник данных продолжает обновляться без подключённого Presenter.
- Игровой счёт начисляется независимо от отображения.
- View показывает переданные данные и не извлекает их из игровых объектов.
- Изменение подписи или числа знаков после запятой не требует менять физику; замена mover не требует переписывать отображение скорости.
- Ты можешь назвать владельца каждой подписки и каждого изменяемого значения.

## Практика C. Начальное состояние, порядок событий и проверка без настоящего UI

### Шаг 8. Разделить состояние и событие

Событие говорит, что что-то произошло; оно не хранит историю для будущего подписчика. Представь, что модель уже содержит скорость 12, а Presenter подключили только сейчас. Откуда возьмётся первое значение на экране до следующего изменения?

Спроектируй первоначальное чтение **всего** состояния после настройки источников и View, а затем обновления по событиям. В текущем `GamePresenter.Init` из источника явно копируется только максимальное число зарядов. Наличие вызова `ChangeHUDStats` ещё не означает, что все переданные поля уже актуальны.

Первоначальное чтение не должно выдумывать данные. Например, `Laser.Init` сохраняет `_startCharges`, но не присваивает его `TotalAmmo`; это делает `ResetParameters`. Сравни старт и рестарт. Если начальное состояние самого оружия неверно по игровым требованиям, его нужно исправлять у владельца состояния, а не рисовать желаемое число только в Presenter.

### Шаг 9. Проверить, что событие сообщает о готовом результате

Открой [Laser.Tick](<C:/Program Files/UnityProjects/Asteroids/Assets/_Project/Sources/Gameplay/WeaponSystem/Laser.cs>). `Ticked` вызывается до обновления `ShootingCooldown` и `ReloadingTime`. Что прочитает обработчик в этот момент?

Поставь breakpoint сначала в обработчике, затем после присваивания этих свойств. Сравни значения в одном вызове. Определи договор уведомления: начало шага или уже изменившиеся данные. Если это событие изменений для UI, порядок должен ему соответствовать. Не компенсируй запоздалые данные пересчётом времени в Presenter.

Это соседняя проблема актуальности данных, а не ещё одно доказательство, что «весь Presenter плохой». Исправляй её отдельным шагом после границ A и B.

### Шаг 10. Замена View на запись вызовов

Для этой проверки интерфейс View получает конкретную пользу. Сформулируй минимальный договор показа и события запроса рестарта. Реализуй учебную замену обычным C#-классом, который запоминает переданные значения и умеет поднимать запрос. TMP, Canvas и Button ему не нужны.

Аналогично подставь простой источник состояния и счётчик запросов рестарта. Проведи сценарии вручную в небольшом тестовом коде или через тестовый фреймворк:

| Сценарий | Что должно наблюдаться |
|---|---|
| Подключение к уже заполненной модели | Сразу показано актуальное состояние |
| Изменение скорости | Показано подготовленное новое значение |
| Запрос View на рестарт | Ровно один вызов игровой команды |
| Окончание игры | Запрос показать результат |
| `Dispose`, затем изменение модели и запрос View | Старый Presenter больше не реагирует |
| Новый Presenter с тем же живым источником | Актуальное состояние, без реакции старого экземпляра |

Нажатие кнопки и настоящий рестарт дополнительно проверь в Unity: обычная замена View проверяет координацию, но не сериализованные ссылки префаба.

При изменении сборки в [SceneScope](<C:/Program Files/UnityProjects/Asteroids/Assets/_Project/Sources/Scopes/SceneScope.cs>) не создавай вторую независимую модель для Presenter. Игра и отображение должны использовать согласованные экземпляры; новый объект, подписанный на игровые события, тоже должен иметь владельца жизненного цикла и отписки.

## Подсказки — после собственной попытки

<details><summary>A. Как выглядит направление событий?</summary>

Кнопка известна View. View поднимает событие запроса, не зная, кто его слушает. Presenter подписывается на это событие и вызывает игровую команду. Для показа он обращается к методам View. Стрелка события не означает, что View должно хранить поле с конкретным Presenter.

</details>

<details><summary>B. Кто собирает игровые данные?</summary>

Связующий объект может знать конкретные компоненты игры и обновлять данные для HUD. Его работа — переводить состояние игры в согласованный набор показателей, без ссылок на экран. Presenter получает этот набор и события, готовит отображение. Если связующий объект начинает управлять ещё и всеми кнопками, спавном и сценами, граница снова потеряна.

</details>

<details><summary>C. Почему недостаточно просто спрятать Button?</summary>

Это исправит второе замечание, но первое останется: Presenter всё ещё может обходить устройство игрока и поддерживать игровой счёт. Обратное тоже верно: хороший источник данных не исправляет прямое управление UI-кнопкой. Проверяй оба критерия независимо.

</details>

## Что показать ментору после занятия

Покажи два маршрута на собственной схеме: запрос рестарта от View к игре и изменение игровых данных к View. Для каждой стрелки назови событие или метод и владельца подписки. Затем продемонстрируй замену View и работу источника данных без Presenter.

Сформулируй объяснение своими словами: «Теперь Presenter отвечает за …; данные собирает …; кнопкой владеет …; правила игры выполняет …; первый показ и отписки устроены …». Если ответ получается только через перечисление названий паттернов, вернись к конкретным сценариям проверки.
